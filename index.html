Learn software testing: beginner pathway

Follow these sections in order. Start with the foundations, practise the core manual-testing skills, then explore broader testing types. The examples use familiar application features; adapt them to your team's process and terminology.

Start here

1. Testing fundamentals

Understand what testing is, why it matters and the basic language testers use.

Learn:
  • Software testing and quality assurance (QA)
  • Defect/bug, error and failure
  • Requirement, user story and acceptance criteria
  • Test scenario versus test case
  • Test data, test environment and build
  • Expected result versus actual result
  • Pass, fail, blocked and not run
Example: A login requirement says a registered user can sign in with valid credentials. The test checks the requirement and compares the actual result with the expected result.
Begin with this

2. Testing approaches

Learn the two broad ways tests are carried out. As a beginner, build confidence with manual testing before moving into automation.

Manual testing

A tester follows steps, interacts with the application, observes behaviour and records results. It is useful for visual checks, usability and exploratory work.

Example: Enter valid and invalid details in a sign-in form and check the messages and navigation.

Automation testing

Scripts and tools run checks and compare results with programmed expectations. It is useful for repeatable checks, APIs and regression suites.

Example: A script repeats the sign-in checks whenever a new build is deployed. Automation helps repeat checks; it does not replace tester judgement.
How to think about tests

3. Testing techniques

These describe how a test is designed and what knowledge the tester uses.

Black-box testing

Test externally visible behaviour without needing to know the source code.

Example: Try valid, invalid and boundary values in a form and check the response.

White-box testing

Use knowledge of internal code and logic to cover statements, branches, conditions, loops and paths. Often associated with developer-level tests.

Example: Check both outcomes of a pricing-rule condition.

Gray-box testing

Test from the outside with some knowledge of internals, such as APIs, data structures or system architecture.

Example: Submit an order through the UI, then verify the related record and event using knowledge of the data flow.
What part is under test?

4. Testing levels

Levels describe the scope of the software being checked. The usual learning order moves from a small component to the whole solution.

Unit testing

Checks one small function or component in isolation. Usually written and maintained by developers.

Example: Check a tax calculation with zero, typical and boundary values.

Integration testing

Checks whether components, services or systems exchange information correctly.

Example: Check that an order service sends the correct payment request and handles success, rejection and timeout.

System testing

Checks the complete integrated application against its requirements.

Example: Complete an end-to-end purchase journey.

Acceptance testing

Checks whether the solution meets agreed business needs and is acceptable for use. UAT is one common form.

Example: Business users confirm that a new workflow supports their real process.
Core tester skill

5. Functional testing

Checks what the application does: features, rules, calculations, permissions, inputs and workflows.

  • Smoke testing: a small, broad set of important checks to see whether a build is stable enough for deeper testing. Example: application opens, login works and key page loads.
  • Sanity testing: a focused check of a particular change or fix. Example: verify a corrected discount calculation and nearby behaviour. Teams may use this term differently.
  • Regression testing: rerun relevant existing tests after a change to check that previously working features still work. Example: after changing checkout, retest related basket and payment flows.
  • Positive testing: check expected behaviour with valid inputs. Example: submit a valid email address.
  • Negative testing: check how the system handles invalid or unexpected inputs. Example: submit a malformed email and confirm a helpful validation message appears.
  • End-to-end testing: check a complete user journey across connected parts of the system. Example: register, place an order and receive confirmation.

Useful test design techniques: boundary value analysis (test at and around limits), equivalence partitioning (group inputs expected to behave alike), decision tables (test combinations of rules) and state transition testing (check valid and invalid state changes).

Quality beyond features

6. Non-functional testing

Checks how well the application works and the quality it provides.

  • Performance: responsiveness, throughput and stability. Example: measure response times during expected use.
  • Load: behaviour under an expected number of users or requests.
  • Stress: behaviour beyond normal operating limits and how the system recovers.
  • Security: protection against unauthorised access and common vulnerabilities. Example: confirm one user cannot view another user's records. Only test within authorised scope.
  • Usability: how easily people can learn and complete tasks. Example: observe a user completing a form and note confusion.
  • Compatibility: behaviour across supported browsers, devices, operating systems and screen sizes.
  • Scalability: ability to handle growth in users, data or workload.
  • Accessibility: whether people with different access needs can use the product, including keyboard and assistive technology support.
Build confidence through practice

7. Exploratory and specialist testing

Exploratory testing

Learn the product, design tests and execute them at the same time. Work to a clear mission or charter, and record observations and evidence.

Example: Explore account recovery using expired links, repeated requests and unusual email formats.

Gorilla testing

Test one module or feature intensively and repeatedly, often with varied inputs. The term is used inconsistently and is not a replacement for a properly defined load or stress test.

Example: Repeatedly test file upload with different file sizes, types and interrupted uploads.

Ad-hoc testing

Informal testing without a detailed test plan, often based on experience and intuition. Record useful findings even when the approach is informal.

Putting it into practice

8. A practical testing workflow

  1. Read the requirement, user story and acceptance criteria.
  2. Ask questions about anything unclear.
  3. Identify risks, scope and what is out of scope.
  4. Write test scenarios and test cases with clear expected results.
  5. Prepare suitable test data and confirm the environment/build.
  6. Execute tests and record actual results and evidence.
  7. Log defects in your team's tool (for example, Azure DevOps) with clear steps, expected/actual results and evidence.
  8. Retest fixes when a new build is available.
  9. Run relevant regression tests.
  10. Summarise coverage, outcomes, risks and blockers.

Remember: follow your team's agreed workflow, severity/priority definitions and entry/exit criteria.

Practice exercises

Try these small exercises as you work through the pathway. You can write your answers in My notes.

  1. Fundamentals: For a password-reset feature, write one requirement in your own words and identify an expected result.
  2. Manual testing: List three steps to test a sign-in form with valid credentials and three steps using invalid credentials.
  3. Techniques: Give one black-box test and one gray-box test for a shopping basket.
  4. Levels: Decide whether checking a tax function, payment API connection, full checkout journey or business approval belongs to unit, integration, system or acceptance testing.
  5. Functional testing: A quantity field accepts values from 1 to 99. Identify useful boundary values to test.
  6. Non-functional testing: Suggest one usability check and one compatibility check for a mobile website.
  7. Exploratory testing: Spend ten minutes exploring a feature and record your mission, actions, observations and any unexpected results.

Testing for beginners: the reference guide

A practical desk reference for the words, activities and habits you will meet as a software tester. Use the search box to find a term. This guide explains common practice; your project may use different names or workflows, so always follow your team's standards.

Showing all reference topics.
The big picture

1. What testing is and why it matters

Software testing is the process of evaluating software to find problems, check requirements and provide information about quality and risk. Testing can reveal defects; it cannot prove that software has no defects.

  • QA (quality assurance): process-focused activities intended to prevent problems and improve how quality is built in.
  • QC (quality control): product-focused activities that evaluate whether the product meets expectations; testing is a major QC activity.
  • Error: a human mistake.
  • Defect / bug: a flaw in a requirement, design, code or other work product.
  • Failure: when the software behaves incorrectly while running.
  • Verification: checking whether work products meet specified requirements (“are we building it right?”).
  • Validation: checking whether the solution meets user needs and intended use (“are we building the right thing?”).

Example: A tester enters a valid email but the application rejects it. Record the observed behaviour and compare it with the requirement.

How work flows

2. Software and testing lifecycles

SDLC means Software Development Life Cycle: the wider process of planning, designing, building, testing, releasing and maintaining software. STLC means Software Testing Life Cycle: the testing activities within that work.

  1. Requirement analysis: understand the feature, rules, risks and acceptance criteria; raise questions early.
  2. Test planning: agree scope, approach, people, timing, environments and risks.
  3. Test design: create scenarios, cases, data and expected results.
  4. Environment and data preparation: make sure the required build, access, integrations and safe test data are ready.
  5. Test execution: run tests, compare actual with expected results and record evidence.
  6. Defect management and retesting: report issues, verify fixes and run relevant regression checks.
  7. Test closure: summarise what was tested, results, outstanding risks and lessons learned.

These activities can overlap and repeat. In Agile teams, testing happens continuously during development rather than only at the end.

Know what to test

3. Requirements and user stories

  • Requirement: something the system must do or a constraint it must meet.
  • User story: a short description of a capability from a user's perspective, often written “As a…, I want…, so that…”.
  • Acceptance criteria: specific conditions that must be satisfied for the story or feature to be accepted.
  • Definition of Done (DoD): the team's shared quality checklist for considering work complete.
  • Scope: what is included in this test effort. Out of scope is what is not being covered, with reasons where useful.
  • Traceability: linking requirements to scenarios, test cases and results so coverage can be understood.

Tester habit: look for missing, unclear, contradictory or untestable requirements. Ask questions rather than guessing. Example: “What should happen after five incorrect password attempts?”

Design your checks

4. Test scenarios and test cases

  • Test condition: an aspect or rule that needs to be checked.
  • Test scenario: a high-level description of what to test.
  • Test case: specific preconditions, steps, test data and expected results for checking one or more conditions.
  • Test step: one action performed during a test case.
  • Precondition: what must be true before starting.
  • Expected result: what should happen.
  • Actual result: what happened when the test was run.
  • Test suite: a group of related test cases.
  • Test script: detailed instructions for a manual test or code that automates a test, depending on context.

Simple example — password reset: Precondition: a registered account exists. Steps: open Forgot password, enter the registered email, submit. Expected: a neutral confirmation message appears and a reset email is sent according to the product rules.

A useful test case is clear, repeatable, focused and has an observable expected result.

Think of useful test data

5. Test design techniques

  • Equivalence partitioning: divide inputs into groups expected to behave similarly; test representative values from each group.
  • Boundary value analysis: test at the edges and just inside/outside limits. If allowed quantity is 1–99, try 0, 1, 2, 98, 99 and 100.
  • Decision table testing: list combinations of conditions and the expected action. Useful for discounts, permissions and business rules.
  • State transition testing: check how a system moves between states and what events cause the transitions. Example: account active → locked after repeated failed logins.
  • Error guessing: use experience to try likely trouble spots, such as blank fields, duplicate submissions or special characters.
  • Pairwise testing: select combinations so every pair of parameter values is covered at least once; useful when many configuration combinations exist.
  • Use-case testing: derive tests from user workflows and interactions.

You do not need to test every possible input combination. Choose tests based on requirements, risk, boundaries and likely usage.

Different kinds of testing

6. Testing types at a glance

Testing labels describe different dimensions and can overlap. For example, a manual black-box regression test can be part of system testing.

  • Functional: checks what the system does — features, calculations, permissions, validation and workflows.
  • Non-functional: checks quality attributes — performance, security, usability, accessibility, reliability and compatibility.
  • Smoke: broad, shallow checks that a build's critical functions work well enough for further testing.
  • Sanity: focused checks around a particular change or fix; teams sometimes use this term differently.
  • Regression: checks existing areas after a change to detect unintended side effects.
  • Retesting / confirmation testing: reruns the failed test for a specific defect after a fix to confirm it is resolved.
  • Positive: uses valid, expected inputs. Negative: uses invalid or unexpected inputs and checks safe, helpful handling.
  • End-to-end: checks a complete workflow across connected components or systems.
  • UAT: User Acceptance Testing; intended users or business representatives check that the solution supports their needs.
  • Exploratory: learning, designing and executing tests together, guided by a mission and observations.
  • Ad-hoc: informal testing without detailed predefined cases.
  • Gorilla testing: intensive repeated testing of one module; usage of the term varies and it is not a formal substitute for performance testing.
Where testing happens

7. Testing levels

  • Unit / component: checks a small function or component, often in isolation.
  • Integration: checks interactions and data exchange between components, services or systems.
  • System: checks the complete integrated product against requirements.
  • Acceptance: checks whether the solution is acceptable for its intended users/business. UAT is a common form.

Think of the scope growing from a small piece of code, to connected pieces, to the full system, to whether the business can use it.

How tests run

8. Manual and automated testing

Manual testing is performed by a person. It is valuable for exploration, usability, visual judgement and situations where human observation matters.

Automation testing uses code or tools to execute checks and compare outcomes. It is useful for repeatable, frequent checks, but needs maintenance and can produce false alarms if poorly designed.

Test pyramid: a common design idea is to have many fast, focused unit tests, fewer integration/API tests and a smaller number of broad UI/end-to-end tests. It is a guide, not a strict rule.

Flaky test: a test that sometimes passes and sometimes fails without a relevant product change, often due to timing, test data or environment instability. Investigate rather than blindly rerunning.

When something goes wrong

9. Defects and bug reports

A good defect report helps someone else reproduce and understand the problem. Include:

  1. Short, specific title.
  2. Environment, browser/device, build/version and relevant account or role (never passwords).
  3. Preconditions and test data, using safe non-production data.
  4. Clear numbered reproduction steps.
  5. Expected result and actual result.
  6. Evidence: screenshot, screen recording, logs or request/response details where appropriate. Remove secrets and personal data.
  7. Frequency: always, intermittent or happened once.

Severity describes the impact/seriousness of the defect. Priority describes how urgently it should be addressed. They are related but not identical; teams define their scales.

Triage is the team's review to confirm, prioritise, assign or otherwise decide how to handle a reported issue. Typical states may include New, Active, Resolved, Closed or Reopened, but workflows differ by team and tool.

Choose what matters most

10. Risk, coverage and prioritisation

  • Risk-based testing: focus effort where failure is more likely or would cause greater harm.
  • Likelihood: how probable a problem is. Impact: how serious the consequences would be.
  • Test coverage: a measure of what requirements, features, risks or code have been checked. Coverage does not guarantee quality.
  • Entry criteria: conditions that should be met before a test activity starts, such as a stable build and available environment.
  • Exit criteria: conditions used to decide when testing can finish, such as planned tests completed and critical defects addressed.
  • Blocker: an issue preventing progress, such as an unavailable environment or missing access.

When time is limited, prioritise critical user journeys, high-impact business rules, changed areas, integrations and historically troublesome features. Communicate what was not tested.

During execution

11. Test results and evidence

  • Passed: actual result matches expected result.
  • Failed: actual result does not match expected result; investigate and raise a defect when appropriate.
  • Blocked: the test cannot be completed because something prevents it.
  • Not run: the test has not been executed.
  • Not applicable: the test does not apply to this build or scope, with a reason recorded.
  • Evidence: information supporting the result, such as screenshots, logs, recordings or captured output.

Always record the build/version, environment, relevant browser/device and test data context. A screenshot can help, but it may not show the full cause; add steps and explanation.

Where and with what

12. Environments, builds and test data

  • Environment: the setup where software runs, including application version, services, configuration and data.
  • Development (DEV): environment used while building software.
  • Test / QA: environment used for formal testing.
  • Staging / pre-production: environment intended to resemble production before release.
  • Production (PROD): the live environment used by real users.
  • Build: a packaged version of the application that can be deployed and tested.
  • Test data: inputs and records used during tests. Use approved synthetic or anonymised data; protect customer information and follow your organisation's policy.

Before testing, confirm you are on the correct environment and build. A result on an old build may not reflect the latest change.

Useful technical basics

13. APIs and web application basics

  • API: Application Programming Interface — a way for software components to communicate.
  • Endpoint: a specific API address/resource.
  • Request: information sent to an API; includes method, URL, headers and sometimes a body.
  • Response: what the API returns, including a status code, headers and possibly a body.
  • Common HTTP methods: GET (retrieve), POST (submit/create), PUT (replace), PATCH (partially update), DELETE (remove). Actual behaviour depends on the API contract.
  • Common status code groups: 2xx success, 3xx redirection, 4xx client/request issue, 5xx server-side issue. Examples: 200 OK, 201 Created, 400 Bad Request, 401 Unauthorised, 403 Forbidden, 404 Not Found, 500 Internal Server Error.
  • JSON: a common text format for structured data exchanged by APIs.

When testing an API, check valid and invalid requests, required fields, data types, permissions, response body, status code and error handling. Do not assume a 200 response alone means the business outcome is correct.

Handy browser tools

14. Browser developer tools

Most browsers include Developer Tools (often opened with F12 or Ctrl+Shift+I; shortcuts vary).

  • Console: shows JavaScript errors, warnings and diagnostic messages.
  • Network: shows requests, responses, timing and failed network calls.
  • Elements / Inspector: lets you inspect page structure and styling.
  • Application / Storage: can show cookies, local storage and session storage.
  • Responsive/device mode: helps preview different screen sizes, though it does not fully replace testing on real devices.

Use these tools to gather evidence and investigate. Avoid sharing tokens, cookies, passwords or personal data from developer tools.

Working with a team

15. Agile and team terminology

  • Agile: an iterative way of delivering work, learning and adapting through feedback.
  • Scrum: an Agile framework with defined accountabilities, events and artefacts.
  • Sprint: a fixed-length period in Scrum during which a usable increment is created.
  • Backlog refinement: clarifying and preparing upcoming work.
  • Sprint planning: agreeing what the team aims to deliver in the sprint.
  • Daily scrum / stand-up: short team coordination meeting.
  • Sprint review: inspect the increment and gather feedback.
  • Retrospective: discuss how the team worked and identify improvements.
  • Stakeholder: a person or group affected by or interested in the product.

Testers collaborate with developers, product owners, analysts and users. Raise risks early and communicate findings clearly and respectfully.

Reporting progress

16. Test metrics and reporting

  • Execution progress: how many planned tests have been run, often split by pass, fail, blocked and not run.
  • Pass rate: passed tests divided by executed tests, using the team's agreed calculation.
  • Requirement coverage: requirements with linked tests/results compared with the total in scope.
  • Defect trends: number, severity, age and status of defects over time.
  • Escaped defect: a defect found after the stage where it was expected to be caught, such as in production.
  • Test summary: scope, build/environment, work completed, results, outstanding defects, limitations, risks and recommendation.

Metrics are signals, not the whole story. A high pass rate does not prove the product is good if important areas were never tested.

Professional habits

17. What makes a good tester?

  • Curiosity: ask what could happen and what assumptions are being made.
  • Critical thinking: consider normal, unusual and boundary situations.
  • Attention to detail: notice small differences and record them accurately.
  • Clear communication: explain impact and reproduction steps without blame.
  • Evidence-led judgement: distinguish what you observed from what you suspect.
  • Risk awareness: prioritise based on user and business impact.
  • Ethics and safety: test only systems you are authorised to test; protect credentials, personal data and confidential information.

You are not expected to know everything. A strong tester asks good questions, documents uncertainty and keeps learning.

Quick reminders

  • Understand the requirement before deciding what to test.
  • Write expected results before execution where possible.
  • Test normal use, invalid use, boundaries and important combinations.
  • Record actual results honestly; do not mark a test passed if it was not fully checked.
  • Separate retesting a fix from regression testing surrounding areas.
  • Report risks and gaps — “not tested” is useful information.
  • Follow your organisation's security, privacy and test-data rules.
